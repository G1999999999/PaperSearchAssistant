# PaperSearchAssistant2 联网搜索、找论文与阅读论文总控改造方案

## 1. 文档目标

这份文档是 `PaperSearchAssistant2` 的总控改造方案，目标是把以下三项能力打通并强化：

1. 联网搜索
2. 找论文
3. 阅读论文

这三项能力不能再彼此割裂，而应形成一条统一工作流：

- 用户先找信息
- 再找论文
- 再选中论文
- 再进入论文阅读与追问

本方案用于指导 Cursor 对项目进行系统级重构。

---

## 2. 当前问题

当前项目虽然已经具备部分：

- 本地 RAG
- arXiv 搜索
- 论文下载
- 论文入库
- 基础问答

但整体上仍存在以下问题：

## 2.1 路由不稳定

用户问：

- `帮我找几篇关于3DGS的最新的论文`

系统可能不会进入“论文搜索”流程，而是误走普通 RAG 问答，然后因为当前上下文没有论文信息而直接拒答。

## 2.2 搜索和阅读没有打通

即使系统找到了论文，也不一定能自然衔接到：

- 下载论文
- 本地入库
- 继续阅读
- 针对该论文连续追问

## 2.3 论文阅读能力不够结构化

现在对论文的处理更像：

- 把 PDF 文本切块
- 放进向量库

而不是把论文建模为：

- 论文主信息
- section
- chunk
- table
- figure

## 2.4 联网搜索能力没有围绕“论文任务”优化

当前联网搜索更多是一个通用 fallback，缺乏针对论文任务的规则：

- 本地优先
- 本地不足自动联网补充
- 搜索结果结构化
- 支持继续阅读

---

## 3. 总体目标

改造后的系统需要满足以下目标：

## 3.1 用户可以自然地“找论文”

例如：

- 帮我找几篇关于 3DGS 的最新论文
- 推荐几篇关于 Gaussian Splatting 的论文
- 最近关于 3D 重建有什么新工作

系统应：

- 优先查本地论文库
- 本地不足时自动联网搜索
- 返回结构化候选结果

## 3.2 用户可以自然地“选中并阅读论文”

例如：

- 读第 2 篇
- 下载这篇
- 这篇论文的方法是什么

系统应：

- 下载 / 打开论文
- 写入本地库
- 建立当前会话的“当前论文状态”
- 支持后续连续追问

## 3.3 用户可以深入问论文内容

例如：

- 这篇论文的核心贡献是什么
- 它的方法怎么做的
- Table 3 结果说明了什么
- Figure 2 的结构图是什么意思

系统应：

- 识别问题类型
- 分别检索正文 / 表格 / 图片
- 融合证据
- 生成可追溯答案

## 3.4 用户可以继续追问和比较

例如：

- 这篇论文和 DPR 有什么区别
- 它的实验结果比 baseline 高多少
- 这张图和正文怎么对应

系统应：

- 维持当前论文阅读上下文
- 支持跨段、跨表、跨图追问

---

## 4. 新的产品工作流

## 4.1 搜索入口

用户问题进入后，系统首先判断是以下哪类任务：

- 普通联网搜索
- 论文搜索
- 论文内容问答
- 本地知识库问答

## 4.2 论文搜索流程

当识别为“找论文”时：

1. 解析主题词
2. 识别是否要求“最新 / 最近”
3. 优先查本地论文库
4. 本地不足时自动联网补充
5. 返回候选论文列表

## 4.3 论文阅读流程

当用户选中一篇论文时：

1. 确认 paper_id 或 arXiv id
2. 如果本地没有 PDF，则下载
3. 入库并结构化解析
4. 设置当前会话的“当前论文”
5. 后续问题默认围绕该论文进行检索

## 4.4 论文内容问答流程

当用户在当前论文上下文中提问时：

1. 判断问题是在问正文 / 表格 / 图片 / 混合
2. 在该论文范围内启动多通道检索
3. 做混合召回、重排与上下文扩展
4. 返回答案并附带证据

---

## 5. 三大能力层级

整个系统应按三层能力建设。

## 5.1 第一层：联网搜索能力

负责：

- 搜索网页
- 搜索论文
- 获取论文元数据
- 获取网页正文
- 获取 PDF

## 5.2 第二层：论文发现能力

负责：

- 本地论文库查询
- arXiv / 网络论文搜索
- 搜索结果去重
- 搜索结果结构化展示
- 论文候选与后续阅读衔接

## 5.3 第三层：论文阅读能力

负责：

- 结构化入库
- 正文问答
- 表格问答
- 图片问答
- 连续追问

---

## 6. 路由层重构

## 6.1 路由必须升级

不能再只依赖简单关键词判断。

建议采用四级路由：

1. 规则短路
2. 论文实体识别
3. SQL 候选召回
4. LLM 语义路由

## 6.2 必须新增的主意图

建议至少支持：

- `web_search`
- `paper_search`
- `paper_read`
- `paper_qa`
- `local_rag`
- `tool_task`
- `casual_chat`

## 6.3 推荐的结构化路由输出

```json
{
  "intent": "paper_search",
  "sub_intent": "latest_topic",
  "topic_query": "3DGS 3D Gaussian Splatting",
  "paper_ids": [],
  "source_preference": "local_first",
  "allow_web_fallback": true,
  "needs_table": false,
  "needs_figure": false,
  "confidence": 0.95
}
```

## 7. 联网搜索能力改造

## 7.1 联网搜索的目标

联网搜索不只是兜底，而是主能力之一。

需要支持两类联网：

1. 通用网页搜索
2. 论文搜索

## 7.2 通用网页搜索

适合：

- 最新新闻
- 最新工具
- 最新网页资料
- 站点信息

联网搜索应支持：

- 多搜索源 fallback
- 结果规范化
- 网页正文抓取
- 摘要提取

## 7.3 论文联网搜索

适合：

- 找某方向论文
- 找最新论文
- 找某作者论文
- 找某主题论文

推荐数据源优先级：

1. 本地论文库
2. arXiv
3. 后续可扩展的学术源

## 7.4 搜索结果必须结构化

每条论文搜索结果至少返回：

- 标题
- 作者
- 摘要
- 链接
- 发布时间
- 来源类型

来源类型建议包括：

- `local`
- `arxiv`
- `web`

---

## 8. 论文搜索默认规则

## 8.1 本地优先

论文搜索类请求默认先查本地论文库。

## 8.2 结果不足自动联网补充

如果本地结果：

- 为空
- 数量不足
- 缺乏最新结果

则在用户未禁止联网时自动联网补充。

## 8.3 “最新 / 最近”是强联网信号

如果用户问题中出现：

- 最新
- 最近
- 近期

则默认开启联网补充，除非用户明确说只查本地。

## 8.4 明确禁止联网时不联网

例如：

- 只查本地
- 不要联网

这时只返回本地结果。

---

## 9. 论文阅读工作流

## 9.1 选中论文后要建立阅读状态

系统必须支持“当前会话当前论文”状态。

建议为 session 维护：

- 当前 paper_id
- 当前 paper title
- 当前 pdf_path
- 当前是否已入库
- 当前是否已建立 chunk / table / figure 索引

## 9.2 当用户说“读这篇”时

系统应执行：

1. 根据候选结果确定目标论文
2. 如果本地未保存，下载 PDF
3. 注册论文主记录
4. 启动解析与结构化入库
5. 更新当前会话的阅读状态

## 9.3 后续追问默认绑定当前论文

当当前 session 已锁定某篇论文时，用户继续问：

- 这篇论文的方法是什么
- 它的实验结果怎么样
- 图 2 讲了什么

系统默认应在该论文范围内检索，而不是全局乱搜。

---

## 10. 论文内容问答能力

## 10.1 论文要结构化建模

论文不能只作为 PDF 文本整体处理。

应建模为：

- paper
- section
- block
- chunk
- table
- figure
- asset

## 10.2 问答必须多通道

论文内容问答必须拆成三类证据通道：

1. 正文通道
2. 表格通道
3. 图片 / 图表通道

## 10.3 正文问答

适合回答：

- 方法
- 贡献
- 实验设置
- 结论

使用：

- 向量检索
- BM25 / FTS
- reranker

## 10.4 表格问答

适合回答：

- Table 2 的结果是什么
- 哪个模型最好
- 某项指标是多少

表格应单独存储并生成摘要。

## 10.5 图片 / 图表问答

适合回答：

- Figure 3 结构图是什么意思
- 这张图展示了什么趋势

图片应单独存储图注、OCR、视觉摘要。

---

## 11. 检索系统必须升级为 Hybrid RAG

## 11.1 为什么不能只用向量检索

如果只用向量检索：

- 精确术语命中会不稳
- 表格编号、图号、指标名容易漏掉
- 很多相关 chunk 排序不稳定

## 11.2 推荐默认方案

推荐默认方案：

- SQL 预过滤
- 向量检索
- BM25 / FTS
- 表格召回
- 图片召回
- RRF 融合
- reranker 重排
- 邻近 chunk 扩展
- MMR 或去重打包

## 11.3 作用划分

- 路由决定检索范围
- SQL 预过滤决定候选集合
- 向量检索负责语义召回
- BM25 负责精确关键词命中
- reranker 负责最终排序

## 12. 数据层改造要求

## 12.1 PostgreSQL

作为主数据库，保存：

- 论文主信息
- sections
- blocks
- chunks
- tables
- figures
- 资源文件
- ingest job
- session
- messages
- attachments
- 当前阅读状态

## 12.2 Chroma

仅用于向量检索。

保存：

- paper chunks
- table summary chunks
- figure summary chunks
- session upload chunks
- summarized chat memory

## 12.3 Redis

保存：

- 当前 session recent history
- 当前 paper detail
- 当前 paper sections
- 当前 paper chunk neighbor cache
- 查询结果缓存
- 下载 / 解析 / embedding 队列

## 12.4 JSONL

仅用于：

- 聊天归档
- 论文入库日志
- 检索 trace
- agent trace

## 16. 实施优先级

建议按以下顺序实施。

## 第一阶段：修正入口和搜索行为

目标：

- 把“找论文”从普通问答中分离出来

任务：

1. 增加 `paper_search` 路由
2. 增加本地优先搜索
3. 增加自动联网补充
4. 统一论文搜索结果格式

## 第二阶段：打通搜索到阅读

目标：

- 让搜索结果能进入“读这篇”

任务：

1. 新增当前论文状态管理
2. 支持候选论文选中
3. 下载 / 入库自动衔接

## 第三阶段：重构论文入库

目标：

- 把 PDF 入库升级成结构化入库

任务：

1. section 解析
2. chunk 生成
3. table 抽取
4. figure 抽取
5. 结构化写库

## 第四阶段：升级论文问答

目标：

- 正文、表格、图片三通道问答

任务：

1. text retrieval
2. table retrieval
3. figure retrieval
4. hybrid fusion
5. rerank
6. context assembly

## 第五阶段：优化和评测

目标：

- 提升性能与稳定性

任务：

1. Redis 缓存
2. latency trace
3. retrieval evaluation
4. answer grounding evaluation

---

## 17. 推荐给 Cursor 的执行顺序

Cursor 应按以下顺序改造：

1. 新增高级路由与 `paper_search`
2. 实现本地优先、结果不足自动联网补充
3. 重构搜索结果结构
4. 增加当前论文阅读状态
5. 打通选中文章后的下载和入库
6. 重构论文结构化存储
7. 增加多通道论文问答
8. 接入 Hybrid RAG
9. 增加缓存与评测

---

## 18. 最重要的结论

要强化“联网搜索 + 找论文 + 阅读论文”，不能只修一个点。

必须整体建立这条主链路：

1. 更强的路由
2. 本地优先的论文搜索
3. 自动联网补充
4. 选中论文后的阅读状态
5. 结构化论文入库
6. 正文 / 表格 / 图片三通道问答
7. 向量检索 + BM25 + reranker 的 Hybrid RAG

最终系统应当从一个“能回答一些问题的 RAG Demo”，升级成一个：

- **能联网搜索**
- **能发现论文**
- **能进入论文阅读**
- **能围绕论文连续追问**

的论文助手系统。
