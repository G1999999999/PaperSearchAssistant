# PaperSearchAssistant2 论文搜索本地优先与联网补充规则

## 1. 文档目标

这份文档用于指导 `PaperSearchAssistant2` 修改“找论文”类请求的默认行为。

核心目标：

- 用户说“帮我找几篇论文”时，不应走普通上下文问答拒答逻辑
- 系统应优先查本地论文库
- 当本地结果不足时，应自动联网补充
- 只有在用户明确禁止联网时，才只查本地

这份文档只讨论“找论文 / 推荐论文 / 最新论文”类请求的行为规则，不讨论论文内容深度问答。

---

## 2. 当前问题

当前系统在遇到如下请求时：

- `帮我找几篇关于3DGS的最新的论文`

实际行为可能是：

- 没有稳定识别为论文搜索任务
- 误走普通 RAG 问答流程
- 只检查当前会话上下文
- 如果上下文中没有论文信息，就直接回答“无法根据当前上下文推荐论文”

这种行为不符合论文搜索助手的预期。

正确行为应该是：

1. 识别这是“论文搜索请求”
2. 优先查询本地论文库
3. 如果本地结果不足，自动联网补充
4. 返回论文候选列表，而不是拒答

---

## 3. 核心原则

## 3.1 “找论文”不是普通 RAG 问答

用户在说：

- 找几篇论文
- 推荐几篇论文
- 最新有哪些论文
- 最近有什么论文
- 帮我搜一下某方向论文

这类请求的本质不是“基于当前上下文回答事实问题”，而是：

- 面向论文库与论文搜索源的检索任务

因此，系统不得把这类请求简单当作：

- 普通本地知识库问答
- 当前对话上下文问答

## 3.2 默认策略必须是“本地优先，结果不足自动联网补充”

当用户发起论文搜索请求时，默认行为必须是：

1. 先查本地论文库
2. 如果本地结果为空或明显不足，则自动联网搜索
3. 合并或补充返回结果

除非用户明确说：

- 只查本地
- 不要联网
- 仅从本地库查

否则系统不能因为当前上下文没有论文信息而直接拒答。

## 3.3 “最新”是强联网信号

当用户请求中出现以下时间敏感词时：

- 最新
- 最近
- 近期
- new
- latest
- recent

这说明用户很可能关心时间上较新的论文。

这时即使本地已有部分结果，也应优先考虑联网补充，除非用户明确禁止联网。

---

## 4. 什么是论文搜索请求

系统必须将以下表达识别为 `paper_search`，而不是普通 RAG 问答：

## 4.1 明确的论文搜索表达

- 帮我找几篇论文
- 推荐几篇论文
- 搜一下论文
- 找几篇关于 XX 的论文
- 最近有哪些 XX 的论文
- 最新的 XX 论文有哪些

## 4.2 含“推荐 / 找 / 搜 / 最新”语义的表达

- 给我推荐几篇 3DGS 的论文
- 帮我找几篇关于多模态 RAG 的最新论文
- 最近关于 Gaussian Splatting 有什么工作

## 4.3 不带“论文”字样但明显是找论文的表达

- 3DGS 最近有哪些 work
- 这方向最近有什么 arXiv
- 有没有最近的 Gaussian Grouping 相关工作

---

## 5. 论文搜索的默认执行流程

对于识别为 `paper_search` 的请求，统一执行以下流程：

## Step 1：解析检索意图

提取：

- 主题关键词
- 时间偏好
- 数量偏好
- 是否要求联网
- 是否要求只查本地

例如：

用户输入：

- `帮我找几篇关于3DGS的最新的论文`

解析结果应类似：

- 主题：`3DGS / 3D Gaussian Splatting`
- 时间偏好：`最新`
- 数量偏好：`几篇`
- 联网要求：`未明确要求，但允许联网`
- 本地限制：`未限制`

## Step 2：先查本地论文库

优先查询本地论文库，来源包括：

- 本地 SQL 论文表
- 本地论文摘要索引
- 本地标题索引
- 本地已入库 arXiv 记录

本地检索应支持：

- 标题匹配
- 摘要匹配
- 关键词匹配
- 时间排序

## Step 3：判断本地结果是否足够

设定“本地结果足够”的规则。

建议阈值：

- 如果用户要求“几篇论文”，而本地结果少于 `3`
- 或者本地结果时间过旧
- 或者本地结果与主题相关性较低

则视为“本地结果不足”。

## Step 4：本地不足则自动联网搜索

如果满足以下条件：

- 用户没有明确禁止联网
- 本地结果不足

则自动发起联网论文搜索。

推荐联网来源：

- arXiv
- 其他论文搜索源（如后续扩展）

## Step 5：合并返回结果

最终返回时可以：

- 先展示本地结果
- 再展示联网补充结果

也可以统一排序后展示，并标注来源：

- 本地库
- arXiv / 联网

---

## 6. 什么时候必须联网补充

以下场景中，如果用户没有明确禁止联网，系统必须联网补充：

## 6.1 本地结果为空

如果本地论文库没有任何相关结果，则必须联网补充。

## 6.2 本地结果数量不足

如果用户希望得到“几篇”论文，而本地只有 1-2 篇结果，则必须联网补充。

## 6.3 用户明确要求“最新 / 最近”

如果问题中有：

- 最新
- 最近
- 近期

则应默认触发联网补充，因为这类问题天然具有时效性。

## 6.4 用户明确要求联网

例如：

- 请联网搜索几篇 3DGS 的论文
- 去 arXiv 找几篇最近论文

这种情况下直接联网，且可以合并本地结果。

---

## 7. 什么时候不应联网

只有以下场景才不联网：

## 7.1 用户明确禁止联网

例如：

- 只查本地
- 不要联网
- 仅从本地论文库找

## 7.2 用户要求的是本地库检查

例如：

- 我本地库里有没有 3DGS 的论文
- 本地已下载的论文里有哪些是 Gaussian Splatting 相关

此时应只返回本地结果，不主动联网，除非用户后续追加要求。

---

## 8. 系统不应出现的错误行为

对于论文搜索请求，系统不应再出现以下行为：

## 8.1 错误行为一：只看当前对话上下文

不能因为当前对话上下文里只有天气记录，就回答：

- “当前上下文没有 3DGS 论文信息，所以无法推荐”

这是错误的，因为论文搜索请求不应依赖当前对话片段作为唯一知识来源。

## 8.2 错误行为二：本地无结果后直接拒答

不能在本地无结果时直接回答：

- “缺乏上下文，因此无法推荐”

正确行为应是自动联网补充。

## 8.3 错误行为三：把论文搜索当作论文问答

“帮我找几篇论文”应返回论文列表，而不是：

- 上下文不足说明
- 长篇知识型回答

---

## 9. 建议的路由输出

对于论文搜索请求，建议路由层输出如下结构：

```json
{
  "intent": "paper_search",
  "topic_query": "3DGS 3D Gaussian Splatting",
  "time_preference": "latest",
  "count_hint": 5,
  "source_preference": "local_first",
  "allow_web_fallback": true,
  "local_only": false,
  "confidence": 0.96
}
```

建议字段：

- `intent`
- `topic_query`
- `time_preference`
- `count_hint`
- `source_preference`
- `allow_web_fallback`
- `local_only`
- `confidence`

---

## 10. 建议的返回结果格式

论文搜索请求返回时，建议统一返回结构化列表。

每条结果应包含：

- 标题
- 作者
- 摘要
- 来源链接
- 发表时间
- 来源类型

来源类型建议标注：

- `local`
- `arxiv`
- `web`

例如：

```json
{
  "results": [
    {
      "title": "...",
      "authors": ["A", "B"],
      "summary": "...",
      "url": "...",
      "published": "...",
      "source_type": "local"
    },
    {
      "title": "...",
      "authors": ["C", "D"],
      "summary": "...",
      "url": "...",
      "published": "...",
      "source_type": "arxiv"
    }
  ]
}
```

## 11. 推荐的代码改造点

## 11.1 路由层

修改路由逻辑，使以下请求稳定进入 `paper_search`：

- 找几篇论文
- 推荐论文
- 最新论文
- 最近论文

不要再把这类请求送到普通上下文问答。

## 11.2 检索调度层

新增或改造一个专门的论文搜索调度器，职责为：

1. 先查本地论文库
2. 判断结果是否不足
3. 自动触发联网补充
4. 合并结果并返回

## 11.3 本地结果充足性判断

增加统一规则函数，例如：

- `is_local_paper_search_result_sufficient(...)`

判断依据包括：

- 结果数
- 相关性
- 时间新鲜度

## 11.4 联网补充入口

联网补充应挂在论文搜索流程里，而不是只挂在普通 RAG 流程里。

也就是说：

- `paper_search` 必须拥有自己的联网 fallback

---

## 12. 推荐给 Cursor 的实施顺序

建议 Cursor 按以下顺序修改：

1. 新增 `paper_search` 明确意图类型
2. 修改路由层，让“找论文 / 推荐论文 / 最新论文”稳定进入 `paper_search`
3. 增加本地论文库优先查询逻辑
4. 增加“本地结果是否足够”的判断函数
5. 当结果不足且用户未禁止联网时，自动触发联网论文搜索
6. 合并本地和联网结果
7. 修改最终返回格式
8. 增加日志，记录：
   - 是否命中本地
   - 是否触发联网补充
   - 为什么触发联网补充

---

## 13. 最终默认行为

改造完成后，以下问题应默认这样处理：

## 13.1 `帮我找几篇关于3DGS的最新的论文`

默认行为：

1. 识别为 `paper_search`
2. 先查本地论文库
3. 如果本地结果不足，则自动联网搜索
4. 返回若干篇论文列表

## 13.2 `推荐几篇 Gaussian Splatting 的论文`

默认行为：

1. 识别为 `paper_search`
2. 先查本地
3. 本地不足则联网补充

## 13.3 `只查本地，看看有没有 3DGS 的论文`

默认行为：

1. 识别为 `paper_search`
2. 只查本地
3. 不联网

## 13.4 `请联网找几篇最新的 3DGS 论文`

默认行为：

1. 识别为 `paper_search`
2. 直接联网搜索
3. 可附加本地结果作为补充

---

## 14. 最重要的结论

对于论文搜索请求，系统默认行为必须从：

- “当前上下文不足就拒答”

升级为：

- **本地优先，结果不足自动联网补充**

也就是说，像：

- `帮我找几篇关于3DGS的最新的论文`

这样的请求，系统必须：

1. 进入论文搜索流程
2. 先查本地
3. 不足则联网
4. 返回论文列表

而不是仅依据当前会话上下文是否已有论文信息来决定是否回答。
